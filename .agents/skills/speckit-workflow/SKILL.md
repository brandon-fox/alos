# SpecKit / Spec-Driven Development (SDD) Workflow Skill

This skill enforces strict compliance with SpecKit / Spec-Driven Development (SDD) workflows across the ALOS repository.

> [!IMPORTANT]
> **MANDATORY DIRECTIVE**: AI agents MUST EXPLICITLY use the SpecKit skill and PowerShell helper scripts for all feature specifications, planning, task definitions, and implementation workflows. Bypassing, skipping, or manually creating spec structures without executing the explicit SpecKit scripts is STRICTLY FORBIDDEN. No implementation code may be written or modified without an active, fully initialized SpecKit feature directory under `specs/<N>-<feature-name>/`.

---

## 1. Explicit SpecKit Skill & Tooling Requirements

Agents MUST strictly use the explicit SpecKit workflow tooling located in `.specify/scripts/powershell/` for every stage of the lifecycle:

| SDD Phase | Explicit Tool / Script | Purpose | Mandatory Usage Rule |
| :--- | :--- | :--- | :--- |
| **0. Prerequisites** | `.\.specify\scripts\powershell\check-prerequisites.ps1` | Verifies environment, Git, and python dependencies | MUST be run before starting a new spec workflow |
| **1. Initialize** | `.\.specify\scripts\powershell\create-new-feature.ps1 -ShortName "<short-name>" "<Description>"` | Bootstraps feature directory and `spec.md` | MUST be executed to create `specs/<N>-<short-name>/` |
| **2. Plan** | `.\.specify\scripts\powershell\setup-plan.ps1` | Creates `plan.md` and `checklists/requirements.md` | MUST be executed before drafting architecture |
| **3. Tasks** | `.\.specify\scripts\powershell\setup-tasks.ps1` | Creates `tasks.md` task breakdown | MUST be executed before defining TDD tasks |
| **4. Environment Setup** | `.\.specify\scripts\powershell\setup-dev-environment.ps1` | Configures virtual environments and tools | MUST be used when setting up dev environments |
| **5. Git Setup** | `.\.specify\scripts\powershell\setup-git-workflow.ps1` | Configures Git branch policies and hooks | MUST be used for SpecKit Git initialization |

> [!CAUTION]
> **FORBIDDEN**: Creating `specs/<N>-<feature-name>/` folders manually or editing spec templates without running the explicit SpecKit PowerShell scripts is a violation of repository rules.

## 2. Canonical SpecKit Directory Structure

Every system feature, capability, refactoring effort, or architectural modification MUST reside inside a dedicated SpecKit folder generated by `create-new-feature.ps1`:

```
specs/<N>-<feature-name>/
├── spec.md              # What & Why: User stories, acceptance criteria, FR-XXX requirements
├── plan.md              # How: Component architecture, API contracts, data models, source layout
├── tasks.md             # Implementation Plan: Atomic, sequential TDD tasks with checkboxes
└── checklists/
    └── requirements.md  # Quality gate & compliance validation checklist
```

The system constitution directives in `.specify/memory/constitution.md` serve as the overarching governance model for all specifications.

## 3. Mandatory SDD Workflow Lifecycle

### Step 0: Check Environment & Prerequisites
Before creating any specification, execute:
```powershell
.\.specify\scripts\powershell\check-prerequisites.ps1
```

### Step 1: Feature Branch & Folder Initialization (Mandatory Script)
Use the explicit SpecKit PowerShell script to bootstrap a new feature branch and directory structure:

```powershell
.\.specify\scripts\powershell\create-new-feature.ps1 -ShortName "<short-feature-name>" "<Detailed Feature Description>"
```

- Auto-increments the feature index (`001`, `002`, etc.).
- Instantiates `specs/<N>-<short-feature-name>/spec.md` from `.specify/templates/spec-template.md`.
- Updates `.specify/feature.json` so downstream tools automatically resolve the active feature path.

### Step 2: Specification Draft (`spec.md`)
Edit `specs/<N>-<feature-name>/spec.md` to define:
- **User Stories & Scenarios**: Plain-language description of desired behaviors.
- **Functional Requirements (`FR-001`, `FR-002`, ...)**: Explicit, unambiguous requirements.
- **Acceptance Criteria & Gherkin Scenarios**: Concrete BDD Given-When-Then scenarios.
- **Non-Functional Requirements**: Performance, security, privacy, and local-first constraints.

### Step 3: Architectural Plan & Checklist (`plan.md` & `checklists/requirements.md`)
Run the explicit setup plan script to initialize the architectural plan and requirement validation checklist:

```powershell
.\.specify\scripts\powershell\setup-plan.ps1
```

Edit `specs/<N>-<feature-name>/plan.md` to document:
- **Technical Architecture & Data Models**: Pydantic v2 schemas and system boundaries.
- **Module & File Layout**: Exact files to create or modify.
- **TDD Test Strategy**: Unit tests and BDD acceptance test mappings (`tests/features/`).
- **Constitution Gate Validation**: Compliance check against `.specify/memory/constitution.md`.

Verify that `specs/<N>-<feature-name>/checklists/requirements.md` accurately lists all `FR-XXX` acceptance criteria.

### Step 4: Atomic Task Breakdown (`tasks.md`)
Run the explicit setup tasks script to initialize the task checklist:

```powershell
.\.specify\scripts\powershell\setup-tasks.ps1
```

Edit `specs/<N>-<feature-name>/tasks.md` to structure execution into ordered, atomic tasks:
- **Task 1**: Write BDD acceptance tests (`tests/features/<feature>.feature`) and pytest suite (`tests/test_<feature>.py`) — **Verify RED (failing)**.
- **Task 2..N**: Implement code modules iteratively — **Verify GREEN (passing)**.
- **Task N+1**: Code quality audit (Ruff lint, Mypy typing, Bandit security, Sonar scan) & Refactor.
- **Task N+2**: Update Architectural Decision Records (`pyadr`) via `pyadr new` if architectural decisions were made.

### Step 5: TDD Execution & Requirement Tracing
- Execute implementation strictly in the order defined in `tasks.md`.
- Check off completed tasks (`- [x] Task description`) as work progresses.
- Ensure every line of added or modified code traces back to an explicit requirement (`FR-XXX`) in `spec.md`.

## 4. Strict Compliance Guidelines for AI Assistants

1. **Explicit SpecKit Skill Execution**: NEVER bypass the explicit PowerShell scripts (`create-new-feature.ps1`, `setup-plan.ps1`, `setup-tasks.ps1`, `check-prerequisites.ps1`).
2. **No Code Before Spec**: Never generate implementation code before creating `spec.md`, `plan.md`, `tasks.md`, and `checklists/requirements.md` via the explicit SpecKit workflow.
3. **Constitution Governance**: All plans and specifications must respect the core principles of `.specify/memory/constitution.md` (Local-first, TDD, Decision provenance, Safety matrix, Fix-first directive).
4. **Git Hygiene & Atomic Commits**: Commit early and often for each completed SpecKit milestone using signed commits and explicit file staging (`git add <file>`). Refer to `git-commit-and-push` skill.
5. **Quality Gates**: Ensure code passes `ruff check`, `mypy`, `bandit`, `pytest`, and Sonar quality scans prior to finalizing the feature.
